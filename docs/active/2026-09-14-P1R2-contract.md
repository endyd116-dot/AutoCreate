## 1. 크론 (B · 서버 자동화)

### [v2.10 · 2026-09-14 B 실측 보고로 정정] 🔴 수동 호출 경로는 `/api/cron-run` 이다
`netlify.toml` 의 `schedule` 로 등록한 함수는 **프로덕션에서 HTTP 로 부를 수 없다**(Netlify 가 막는다). 게다가 `netlify dev` 는 그 요청을 «실행은 시키고 응답 본문은 버린다» — 그래서 «일은 다 됐는데 `ran` 이 undefined» 라는 **가짜 증상**이 난다.
```
(스케줄 전용 · HTTP 호출 불가 · config.path 없음)
  netlify/functions/cron-tick-5m.ts      — Netlify scheduled 만 부른다
  netlify/functions/cron-tick-hourly.ts

(사람·검증용 정본)
POST /api/cron-run?every=5m|hourly&secret=$CRON_SECRET     ← 🔴 C·스모크·수동 실행은 전부 이 경로
  → { ok:true, ran:[{ step:string, tenants:number, changed:number, skipped:number, errors:number, detail?:object }] }
```
- [v2.11 · C 열린 질문 확정] **quietDays 를 나중에 지정하면** 그 날의 슬롯은 «**글 안 붙은 planned 만 삭제**, 소재·글이 붙은 것은 유지» — 이미 만든 글을 조용히 버리지 않는다(코인이 들어간 것). 유지된 슬롯은 달력에 «쉬는 날에 잡힌 글» 표시로 사람이 옮기거나 건너뛴다.
- 스텝 로직은 **`runTick()` 한 벌** — 스케줄 함수와 `cron-run` 이 같은 함수를 부른다(로직 이중화 0).
- `cron-tick-*` 에 `config.path` 를 두지 않는다 — 두면 «있는데 안 되는 경로»가 되어 다음 사람이 조용히 빈 응답을 받는다.
스텝 계약(각 스텝은 테넌트 단위 격리 · 한 집 실패가 전체를 굶기지 않는다 · 전건 audit):
| step | 주기 | 하는 일 |
|---|---|---|
| `slots.roll` | hourly(하루 1회분 멱등) | `rollSlots(tid, horizonDays)` — R1 함수 그대로 · quietDays·bestTimeMode 반영 |
| `slots.assign_topics` | hourly | `topicLeadDays` 안의 `planned` 슬롯에 소재 배정(없으면 `topics.refresh` 자동 1회 → 그래도 없으면 status `no_topic` + 알림) · 30일 중복 회피 |
| `slots.produce` | hourly(`produceHour` 시각에만) | `produceLeadDays` 안의 `topic_assigned` → 디렉터 brief(자동 모드) → piece 생성 + 코인 consume(**weeklyCoinCap 초과면 status `coin_short` + 알림 · 원장 무접촉**) → 배경 생성 호출 → 슬롯 `producing` |
| `slots.review_deadline` | hourly | `reviewPolicy==="silence_approves"` 면 발행일 02:00(KST) 까지 미반려 in_review → approved+scheduled · `require_confirm` 이면 D-0 08:00 알림만 |
| `publisher` | 5분 | due(`scheduled` ∧ publish_at ≤ now) → API 채널이면 즉시 발행(B2 커넥터) · 러너 채널이면 `runner_jobs` 적재 후 `publishing` · 러너 오프라인 30분+ 면 `awaiting_runner` 표기(발행 취소 아님) |
| `slots.learn` | hourly | 발행 후 6·24·72h 지난 post 의 조회·좋아요·댓글 회수(API 채널=API · 러너 채널=`revenue.stats` 잡) → `posts.stats` · topic factors.performance 갱신 |
| `runner.reap` | 5분 | claim 후 15분 무보고 job 회수(release) · 계정 `pending_login` 판정 유지 |

## 2. 러너 서버측 (B2)
```
POST /api/runner-register  body { name, kind:"own" }  (로그인 세션)    → { ok:true, device:{ id, name, token }, install:{ cmd, url } }   // token 은 이때 1회만 평문
GET  /api/runner-list                                                   → { ok:true, devices:[RunnerDevice] }
POST /api/runner-remove    body { id }                                  → { ok:true }
POST /api/runner-heartbeat header x-runner-token  body { version, jobs:number }
  → { ok:true, sleepSec:number }
POST /api/runner-queue     header x-runner-token  body { action:"claim"|"report"|"release", ... }
  claim   { action:"claim", kinds:[RunnerJobKind], max:number }         → { ok:true, jobs:[RunnerJob] }
  report  { action:"report", jobId, result:{ ok:true, externalUrl?, channelRef?, stats? } | { ok:false, errorKind:RunnerErrorKind, detail?, shotKey? } } → { ok:true }
  release { action:"release", jobId, reason }                           → { ok:true }
POST /api/runner-session-upload header x-runner-token body { accountId, cookies:[...], verifiedAt } → { ok:true }   // 헤드풀 로그인 결과 · 암호화 저장 · 계정 active 승격
RunnerDevice = { id, name, kind, status:"online"|"offline", lastSeenAt?, version?, jobsWaiting:number }
RunnerJob = { id, kind, accountId?, pieceId?, payload:RunnerPayload, account:{ handle, channel, profileKey, proxyUrl?, cookies?:[...] }, priority }
RunnerJobKind = "publish.naver_blog" | "publish.tistory" | "session.login" | "session.verify" | "verify.post_alive" | "revenue.stats"
RunnerErrorKind = "login_fail" | "captcha" | "rate_limited" | "suspended" | "selector_changed" | "network" | "unknown"
RunnerPayload(publish.*) = { title, bodyHtml, blocks, images:[{ url, caption }], tags:[string], disclosure:string|null, scheduledFor }
```

- claim 은 원자 선점(`FOR UPDATE SKIP LOCKED`) · 우선순위 발행 > 세션 > 통계 · report 는 러너 주장을 믿지 않는다(URL HEAD/본문 확인 후 `published`).
- 실패 분류(`lib/runner-block.ts` — AM 이식) → 계정 상태 전이(§4).

## 3. 발행 커넥터 (B2)
```
lib/publish/index.ts  publish(piece, account) → { ok:true, externalUrl, channelRef, via:"api"|"runner" } | { ok:false, reason, retriable }
  · blogger.ts    Blogger v3 posts.insert(OAuth 토큰 · 리프레시 자동)
  · wordpress.ts  POST {site}/wp-json/wp/v2/posts (Basic · App Password) · 이미지는 media 업로드 후 본문 치환
  · naver_blog.ts · tistory.ts  = 러너 잡 적재(서버에서 직접 발행 불가)
```
- 발행 직전 최종 게이트(§16B): 고지 첫 요소 **복원**(없으면 정본 문구 삽입) · 금칙어 · 제휴 링크 ≤2 — 실패면 `awaiting_manual` + 알림(발행 금지).
- [v2.5] **애드센스 블록 실체화**(P1R1 §4B 가 «발행 커넥터 R2» 로 미뤄 둔 것): `<div class="adsense"></div>` → 계정 애드센스 코드 + «광고» 라벨. 키 없으면 그 자리를 제거 · 네이버 블로그는 애드포스트라 제외.
- [v2.5] **게이트가 고친 본문은 `pieces.body` 에 저장한다** — «올린 것 = 저장된 것»(검수 화면과 발행물이 갈리지 않는다).
- [v2.5] 🔴 **발행 성공 + finalize 실패 = `{ ok:false, reason:"config", retriable:false }`** — 재시도하면 중복 글이 남는다. B 의 publisher 는 재시도하지 않고 종결 + 알림. 감사 `publish_finalize_failed`(risk high).
- [v2.5] finalize 멱등은 조건부 UPDATE 선점(`WHERE external_url IS NULL AND channel_ref IS NULL AND status<>published`) — API 성공과 러너 report 가 동시에 와도 posts 1행.
- 멱등: piece.channel_ref/external_url 있으면 재발행 0(로그만) · 성공 시 `posts` 행 + piece `published` + slot `published` + 계정 `posts_today++`·`last_post_at`.

## 4. 계정 전이·승계 (B)
```
lib/account-health.ts
  classifyAndApply(accountId, errorKind) → { status, action:"cooldown"|"relogin"|"suspend"|"none" }
  reassignSlots(accountId) → { moved:number, targets:[{ slotId, toAccountId }] }   // suspended 시 같은 채널·그룹의 건강한 계정으로 · 코인 0 · 앵글 재변주는 produce 가 처리
```
- `suspended` → 예약 슬롯 재배정 + 알림 «@a 계정이 정지됐어요 · 글 N건을 @b 로 옮겼어요»
  🔴 [v2.4] **`reassigned` 의 뜻(메인 확정)**: 슬롯 = «그 시각·그 계정으로 나갈 한 자리»의 원장.
  · 아직 안 나간 자리(planned~scheduled) = **행을 살리고 계정만 바꾼다**(상태 보존 — 닫으면 그 글이 영영 안 나간다).
  · 이미 `publishing` 인 자리 = 되돌릴 수 없으니 그 행을 **`reassigned` 로 종결**하고 이어질 몫은 **새 슬롯 행**(달력에 «@a 넘김»·«@b 예약» 둘 다 남는 게 정직). DESIGN §5B.6 의 `publishing → reassigned` 화살표가 이 경우다.
  🔴 [v2.4] **전이표 정본 = `lib/account-health.ts`**(B) — `RunnerErrorKind`·`ACCOUNT_ACTION_OF`·`STATUS_OF_ACTION`·`RUNNER_ERROR_LABEL` export. B2 의 `runner-block.ts` 는 «날것의 실패 → RunnerErrorKind» 까지만 하고 이 표를 **import** 한다(방향 B2→B · 순환 0).
- `captcha|login_fail` → `pending_login` + `session.login` 잡 적재 + 홈 todo
- `rate_limited` → `cooldown` 24h + daily_cap −1
- health_score = 최근 30일 성공률 − 경고 − 발행 후 삭제(verify.post_alive) · 0~100.
