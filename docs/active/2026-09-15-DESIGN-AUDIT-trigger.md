## 1. 상태 어휘(고정 · 이것만 쓴다)

| 기호 | 뜻 | 조건 |
|---|---|---|
| ✅ 됨 | 코드 + 화면 + 증거 | 파일:줄 **과** 화면 경로 **과** (실측했으면) URL/row id |
| 🟡 코드만 | API·로직은 있는데 화면에서 못 쓴다 | CLAUDE §4.8 «완료 = 화면에서 쓸 수 있을 때» 위반 |
| 🟠 있지만 안 됨 | 화면·코드 다 있는데 실측에서 안 되거나 반쪽 | «무엇이 안 되는지» 한 줄 필수 |
| 🔒 외부 선결 | 키·앱 심사·법 절차가 막음 | 코드가 «키 꽂으면 즉시 가동» 상태인지 **병기**(아니면 🟡/❌ 로) |

## 2. 행 형식(표 한 줄 = 판정 단위 하나)

```
| DESIGN § | 항목(설계 원문 요약 · ≤40자) | 상태 | 증거(파일:줄 · 화면 경로 · 실측 URL/row) | 안 되는 것(한 줄) | 남은 일(한 줄) | 크기 S/M/L |
```

- 크기: S = 반나절 · M = 하루 · L = 라운드.

## 3. 절차

1. `docs/DESIGN.md` 를 **§0 → §19 순서로 통독**한다(84KB · 이 조사만은 통독이 맞다). §마다 판정 단위로 쪼개 표를 먼저 만든다(상태는 비워 둔다).
2. 단위마다 코드를 `grep`·읽기로 찾아 증거를 적는다. 화면은 `public/app/*.html`·`public/ops/*.html` 에서 **«고르는 UI가 있나»**까지 본다 — API 만 있으면 🟡.
3. 실측 가능한 것은 `netlify dev` + **테스트 테넌트만**으로 1회 호출(LLM·이미지·영상 실호출 금지 — `VIDEO_PROVIDER_STUB=1` · 글 생성은 스텁이 없으니 호출하지 않는다). 못 재면 ⬜.
4. 🔴 **특별 항목 3개(사장님이 짚은 것) — 표와 별도로 «절»을 하나씩 쓴다**

   - **b. «기능은 있지만 제대로 안 되는 것»**: 고객 여정 1바퀴(가입 → 계정 연결 → 소재 → 디렉터 → 글 → 검수 → 편성표 → 발행함 → 수익 → 요금제·코인 → 설정·내보내기)를 **화면으로 직접 눌러 보며** 걸리는 곳을 전부 적는다(스샷 `_shots/audit-*.png`). 러너·발행은 `--peek`/드라이런만.
