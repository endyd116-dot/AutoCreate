## 4. 🔴 «정확히»가 되려면 남은 실측 2개

이 문서의 숫자는 **공급사 공개가 + 사용량 가정**이다. 다음 두 가지가 실측되면 «정확히»가 된다.

1. ~~계정 1개가 한 달에 쓰는 트래픽(GB)~~ → **✅ 실측했다(B2 · 2026-09-15). 아래 §4.1 로 대체.**
2. **한국 IP 실구매 견적 3곳** — 공개가는 «부터»다. 계정 10개·20개·50개로 **실제 견적**(한국 재고 · sticky 보장 · 대역 상한 · 결제 조건)을 받아 표를 채운다. 실제 구매는 사장님 합동 세션 11번.

### 4.1 ✅ 트래픽 실측(B2 · 2026-09-15 · 러너 계측기 `meterContext`)

측정 방법: Playwright 컨텍스트에 CDP 를 붙여 **`Network.dataReceived`(encodedDataLength)** 를 합산했다 —
전선 위 실제 바이트다(`response.body().length` 로 세면 **압축 풀린 크기**라 3~5배 과대계상된다).
업링크는 정확한 신호가 없어 **요청 본문 길이 합**으로 근사했다(헤더·TLS 제외 — 이미지가 업링크의 거의 전부라 «몇 MB냐»는 맞는다).

| 잰 것 | 실측 | 비고 |
|---|---|---|
| 네이버 블로그 **글 1장 열기** | **↓1.24MB** (요청 133건) | `verify.post_alive` 가 하는 일 = 이 값 |
| 네이버 **글쓰기 진입**(로그인으로 튕김) | **↓3.21MB** (요청 21건) | 🔴 로그인 화면 기준 **하한** — 진짜 에디터는 이보다 무겁다 |
| 티스토리 첫 화면 | ↓2.73MB ↑117KB (요청 82건) | 참고값 |
| **생성 이미지 1장**(실제 R2 자산 24장) | **평균 0.76MB** (중앙값 0.77 · 0.65~0.87) | 업링크의 거의 전부 |
| **글 1건 이미지 6장 업로드** | **↑4.59MB** | 10장이면 ↑7.65MB |

**글 1건 합계(추정 · 실측 부품 조립)**: 에디터 진입 ↓3.2MB + 이미지 ↑4.6MB + 저장·발행 왕복 ~0.5MB ≈ **9~10MB/건**.

🔴 **가정(20~40MB)의 2~4배 과대였다.** 월 트래픽을 다시 계산하면:

| 하루 발행 | 월 건수 | 월 트래픽/계정 | GB 과금($2/GB 기준) |
|---|---|---|---|
| 1건 | 30 | **≈0.29GB** | ≈₩800 |
| 2건 | 60 | **≈0.58GB** | ≈₩1,600 |
| 3건 | 90 | **≈0.87GB** | ≈₩2,400 |

**결론(가격 결정 입력)**: 글 채널만 쓰는 계정은 트래픽이 **1GB 미만**이라 **GB 과금이 IP 과금(₩3,400~7,000)보다 싸다.**
다만 §2 표의 🟡 대로 **회전 주거용은 sticky 가 끊기면 IP 가 바뀌어** 계정-IP 1:1 이 깨진다 —
**싼 쪽이 아니라 «IP 가 안 바뀌는 쪽»을 골라야 한다**는 판단은 그대로다. GB 과금을 쓰려면 **sticky 보장**이 계약 조건이다.
⚠️ 영상(쇼츠) 계정은 이 표 밖이다 — mp4 업로드가 한 건에 수십 MB라 따로 재야 한다.

⚠️ **아직 안 잰 것**: 로그인된 **진짜 에디터**의 무게(위 3.21MB 는 로그인 화면이다). 계측기는 러너에 **상시로** 들어갔으니,
합동 세션의 첫 실발행이 돌면 그 값이 `report.bytes` 로 **자동으로** 남는다 — 그때 이 표를 확정한다.

## 5. 정직하게 말할 것(화면·안내 문구)

- IP 를 나눠도 **유튜브·인스타·쓰레드는 우리 서버에서 API 로 올라간다** — 그쪽은 IP 보다 **우리 앱·계정 신호**로 묶인다. «IP 를 나눴으니 정지가 안 된다»고 말하면 안 된다.
- 프록시가 죽으면 **그 계정은 멈춘다**(우리 IP 로 대신 나가지 않는다 · fail-closed). 이게 정지 연쇄를 막는 핵심이라 «가끔 멈출 수 있다»를 미리 알린다.
- IP 는 **빌리는 것**이다 — 공급사 사정으로 바뀔 수 있고, 바뀌면 그 계정은 새 IP 로 다시 묶인다(기록·알림).

## 6. 사장님 질문 2026-09-15: «동적 IP 로 더 싸게 안 되나 · IP 말고 다른 방법은?»

### 6.1 동적 IP(집 회선 재접속으로 IP 바꾸기) — **싸지만 이 용도엔 오히려 나쁘다**
| | 내용 |
|---|---|
| 비용 | **0원**(이미 있는 회선) |
| 되는가 | 공유기 WAN MAC 을 바꾸고 재접속하면 새 IP 를 받는 경우가 있다. 다만 한국 ISP 는 **같은 IP 를 다시 주는 일이 흔하고**, 바뀌어도 **같은 ISP·같은 대역 안**이다 — 플랫폼은 대역 단위로도 본다 |
| 🔴 치명적 1 | **계정–IP 1:1 고정이 깨진다.** 네이버·메타는 «항상 같은 곳에서 접속»을 정상으로 보고 **«매번 다른 IP 에서 로그인»을 이상 신호로 본다** — 돌릴수록 위험해질 수 있다(효과가 반대로) |
| 🔴 치명적 2 | **한 회선은 한 번에 IP 하나** — 계정 10개를 «IP 10개»로 못 만든다. 순차로 돌려야 하고 재접속마다 전체가 끊긴다 |
| 결론 | 계정 여러 개를 가르는 용도로는 **쓰지 않는다**. «계정 1~2개 + 자기 집 IP 고정»이면 애초에 프록시가 필요 없다(6.3) |

### 6.2 🟢 **모바일 회선 자체 구축 — 지금까지 중 가장 싸다**
모바일(LTE/5G)은 통신사 CGNAT 라 **IP 하나를 수천 명이 공유**한다 → 플랫폼도 «모바일 IP 공유»를 정상으로 본다. 그래서 **계정마다 IP 를 1:1 로 줄 필요가 없다** — 이게 정적 주거용과 결정적으로 다른 점이고, 원가를 한 자리 낮춘다.

| 항목 | 금액 | 메모 |
|---|---|---|
| 알뜰폰 데이터 회선(20GB급) | **정가 월 ₩19,800~24,200** · **프로모션 6~7개월 월 ₩10~900** | 2026-09 실조사 |
| 기기(4G 라우터 또는 안 쓰는 공기계 + 테더링) | 1회 **₩0~150,000** | 노트북 옆에 두면 된다(관리형 구조와 정확히 맞는다) |
| 우리 트래픽 | 계정당 월 **0.6~1.2GB 추정** → 20GB 면 **계정 10~20개** | 🔴 실측 예정(B2) |
| **계정당 월 원가** | **₩1,000 ~ 2,400**(정가 기준) · 프로모션 기간엔 거의 0 | 정적 주거용(₩5,000)의 **1/2~1/5** |
| 단점 | 회선·기기를 우리가 관리(교체·재부팅·요금제 갈아타기) · 계정 «시간차»로 써야 함 · IP 가 자주 바뀐다(모바일에선 정상) | |

⇒ **권장: 관리형은 모바일 회선 1~2개로 시작**(계정 10~20개 커버) · 특별히 중요한 계정만 정적 주거용 IP 1:1.

### 6.3 🔴 IP 보다 싸고 효과 큰 방어 6개(순서대로)
플랫폼이 보는 신호에서 IP 는 **여섯 번째쯤**이다. 아래가 앞이다.
1. **계정 워밍업** — 새 계정을 바로 쓰지 않는다. 2~4주에 걸쳐 «주 1건 → 주 2건 → 하루 1건»으로 올린다. **0원 · 효과 최대**(대량 정지의 1번 원인이 «새 계정이 첫날부터 많이 쓴다»). **우리가 자동으로 해 줄 수 있다 → R7 §2.6**
2. **발행량·간격** — 하루 1건 · 간격 랜덤 · 새벽 금지. 이미 `daily_cap`·`min_gap_min`·계정 간 30분이 있다(값을 워밍업과 연동)
3. **콘텐츠** — 중복·홍보성·링크 과다 회피. 이미 유사도·금칙어·AI티·고지 게이트가 있다
4. **계정 자체의 나이·실사용 흔적** — 오래되고 실제로 쓰던 계정일수록 안 죽는다(새로 파서 몰아 쓰는 게 제일 위험)
5. **브라우저 프로필 격리** — 이미 계정별 영구 프로필(쿠키·지문)
6. **IP 분리** — 여기서 처음 돈이 든다
7. (보험) **계정 그룹 승계** — 하나 죽어도 같은 니치의 다른 계정으로 예약이 넘어가 **수익이 안 끊긴다**(§2.5-7)

| 어뷰징 문서는 검색 배제 + **삭제해도 페널티 이력이 남는다** | 검색 정책 해설 | 🟡 2차 자료 |
| «여러 계정이 N분 안에 올리면 제재» | — | ❌ **못 찾았다** |

🔴 **그러므로 «30분»도 «5분»도 추정이다.** 통설이지 근거가 아니다. 코드에 있던 30 은 주석에도 근거가 없었다.
🔴 그리고 더 큰 것이 드러난다: **간격이 문제가 아니라 «자동 게재» 자체가 약관상 금지**다.
   우리 러너는 그 일을 한다 — 그래서 우리가 지키는 것은 «규칙»이 아니라 **«탐지되지 않을 만큼 사람처럼»**이다.
   ⚠️ 이건 제품 전체에 걸린 사실이라 **약관 법률 검토 때 같이 물어야 한다**(체크리스트 §3-2).

#### ② IP 가 다르면 얼마나 줄어드나 → **추정**(공식 근거 0)
§6.3 의 순서에서 IP 는 **여섯 번째**다. «동시 발행»은 **2번(발행량·간격)** 안에 든다 — 즉 **IP 보다 앞**이다.
그래서 «IP 만 나누면 동시에 올려도 된다»는 성립하지 않는다. 다만 **같은 IP 에서 동시**보다는 **다른 IP 에서 동시**가 신호가 약한 것은 맞다(추정).

#### ③ 지금 우리가 이미 막고 있는 신호

| 신호 | 막고 있나 | 어디 |
|---|---|---|
| 새 계정이 첫날부터 많이 쓴다 | ✅ 워밍업(주 1·2·3건 → 정상) | `lib/warmup.ts` |
| 하루 발행량 | ✅ `daily_cap`(워밍업이 유효값을 낮춘다) | `lib/accounts.ts` |
| 같은 계정 연속 발행 | ✅ `min_gap_min` | 계정 설정 |
| **계정 간 동시 발행** | ✅ 30분(채널 단위) | **이 절** |
| 같은 IP 로 여러 계정 | ✅ 계정 1:IP 1 · fail-closed · **출구 IP 실측** | `lib/proxies.ts` · `runner/lib/browser.mjs` |
| 같은 기기에서 여러 계정 | 🟡 프로필 격리(쿠키·지문)는 있다 · **기기 지문은 계정이 아니라 러너 단위** | `runner/lib/browser.mjs` |
| 비슷한 글·제목 | ✅ 유사도 축(`similarity`) · 골격 반복 | `lib/video/judge.ts` · B-1 §2 |
| 같은 시각 반복(매일 정각) | 🟠 **안 막는다** — 후보 시각에 랜덤이 없다(`shift` 는 충돌 때만) |
| 사람 없는 시간대(새벽) | 🟠 **안 막는다** — 후보 표에 새벽이 없을 뿐, 규칙으로 금지하진 않는다 |

⇒ 🔴 **표에서 두 칸이 비어 있다**(같은 시각 반복 · 새벽). 간격을 좁히기 전에 이 둘이 더 싼 방어다.

#### 그래서 어떻게 했나 — `lib/publish-gap.ts`
**상수를 5 로 내리지 않았다.** 추정 위에 새 상수를 박으면 지금 30 이 그랬던 것처럼 또 근거 없는 값이 생긴다.
대신 **우리가 실제로 잰 것**에만 기대어 폭을 준다:

| 상태 | 고객이 내릴 수 있는 바닥 | 왜 |
|---|---|---|
| 그 채널에 계정 하나뿐 | 5분 | 부딪힐 상대가 없다 |
| 프록시 없음(같은 집 IP) | **30분** | 연좌제의 원인 |
| 프록시 배정만 · **출구 IP 미측정** | **30분** | 🔴 «배정됨»을 «다르다»로 읽지 않는다 — 프록시는 죽어 있을 수 있다(AC-57) |
| 상대 계정의 IP 를 아직 못 쟀다 | **30분** | 🔴 모르는 쪽을 유리하게 읽지 않는다(AC-9) |
| 실제로 **같은** IP 였다 | **30분** | 프록시가 있어도 같으면 소용없다 |
| ✅ **전부 실측 · 전부 다르다** | **5분** | 여기서만 폭을 준다 |

🔴 **우리가 자동으로 좁히지 않는다 — 고객이 고른다.** 대신 `risk` 한 줄을 같이 내려보내 화면이 위험을 말한다.
검사: `scripts/verify-publish-gap.mts` **8/8**(음성 대조 = «모르면 안 준다» · «전부 막으면 기능이 없다» · 근거·문구가 갈리는지).

### 6.4 그래서 계정 수별 권장
| 계정 수 | 권장 | 계정당 월 원가 |
|---|---|---|
| **1~3개**(고객 자기 PC) | **프록시 불필요** — 자기 집 IP 그대로가 가장 자연스럽다 + 워밍업·발행량 규율 | **₩0** |
| 4~10개 | 모바일 회선 1개(자체) + 시간차 · 워밍업 필수 | ₩1,000~2,400 |
| 10개 이상 / 관리형 | 모바일 회선 2개 + 중요 계정만 정적 주거용 1:1 | ₩2,000~5,000 |

## 7. 관리형 = 프록시 + 러너 실행 분담(P1R7 §2.4 · B3 2026-09-15 · 숫자 없음)

> 이 절은 **숫자를 적지 않는다.** 값은 코드 상수 한 곳에만 있고, 여기는 «무엇이 그 값에 들어 있고 어디를 읽으면 되나»만 말한다(두 곳에 적으면 하나가 썩는다).

- **고객이 세는 단위는 계정이다(대수 아님)** — 신청 표 `managed_runner_requests.accounts`(DDL [`drizzle/0018-r7-managed-per-account.sql`](../../drizzle/0018-r7-managed-per-account.sql) · `devices` 는 옛 칸, 지우지 않는다 · `amount_krw` = 계정당 공급가 스냅샷). 상한도 `plan.limits.maxAccounts`(계정 수)다 — `runnerDevices`(기기 수)로 막으면 단위가 다른 값으로 막는 버그.
- **계정당 월요금에 무엇이 들어 있나**: ① 전용 IP(프록시) — **포함**(사장님 결정 4 · 따로 받지 않는다) ② 우리 서버 러너 실행 분담(노트북 1대가 계정 N개를 돌리는 전기·감가·대역의 1/N) ③ 운영(IP 교체·장애). **AI 생성 원가(글·이미지·영상)는 없다** — 코인으로 따로 받는다(이중 과금 금지). 원가 분해 행은 위 §2 표의 «관리형» 한 줄뿐이다.
- 🔴 **값의 단일 출처 = [`lib/plans.ts`](../../lib/plans.ts) `MANAGED_RUNNER_ACCOUNT_KRW`**(계정당 권장 공급가 · 부가세 별도 · 프록시 포함). 플랜별 **실부담**은 `managedRunnerUnitKrw(plan)`(`managedRunner: option` = 유료 · `included` = 0원 · `no` = 못 씀). 화면·API 는 이 둘만 읽는다 — `netlify/functions/managed-runner.ts` 의 `shownUnit`(못 쓰는 플랜엔 안내용 정가, 청구는 언제나 `unit` 스냅샷).
- 🔴 **«확정»이 아니다.** 결정 7(가격)은 합동 세션 12번에서 사장님이 정한다. 확정되면 **상수 한 줄만** 고친다 — 이 문서·화면·API 에 숫자를 다시 적지 않는다.
- **모바일 회선 자체 구축(§6.2)과의 관계**: 관리형 1호기가 정적 주거용 IP 대신 **모바일 회선을 쓰면 원가는 그만큼 내려간다 · 값은 그때 재측정**(§4.1 트래픽 실측 = 회선 1개가 계정 몇 개를 덮는지의 입력). 원가가 내려가도 공급가(상수)를 자동으로 따라 내리지는 않는다 — 그것도 결정 7.
- **기기가 죽으면 우리가 안다**: [`lib/cron/managed-runner-watch.ts`](../../lib/cron/managed-runner-watch.ts) 스텝 `managed.watch`(5m · **global** — 관리형 기기는 `tenant_id IS NULL` 이라 테넌트 루프에선 안 보인다) → 운영 감사. 관리형은 고객이 켤 수 없으니 «고객 화면에만 조용히» 는 금지(AC-9).
