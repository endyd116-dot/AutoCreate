# 셀렉터 표(recipe) 서버 배포 — 카나리 설계 · 2026-09-15 (B2 · R8 선결 · **문서만 · 코드 0**)

> 메인 지시: «①recipe 버전·서명·롤백 ②카나리 대상 선정 ③실패 판정과 자동 복귀 ④부분 배포 ⑤시간 게이트 ⑥운영 화면 신호».
> 🔴 **R8 항목이라 코드는 쓰지 않았다.** 설계가 서면 발주받는다.

---

## 0. 🔴 먼저 고쳐 쓴 것 — «카나리»는 **이미 있다**. 그런데 **다른 물건**이다

초안을 백지에 썼다가 코드를 읽고 버렸다. 이 프로젝트에는 이미 카나리가 **둘** 있다.

| 있는 것 | 무엇을 하나 | 어디 |
|---|---|---|
| **셀렉터 카나리** | «**오늘** 채널 화면이 그대로인가» — 우리 테스트 계정으로 임시저장까지 드라이런 | `canary_runs` · `lib/cron/runner-canary.ts` · `ac-runner --canary` |
| **AI 모델 카나리** | «**새 판**을 일부에게 먼저» — candidate 10% → 24h 관찰 → 승격/자동롤백 | `ai_model_overrides` · `lib/cron/ai-model-watch.ts` |

**내가 설계해야 하는 recipe 카나리는 두 번째 종류**(새 판 배포)인데, 이름과 표는 첫 번째 것과 겹친다.
⇒ 이 설계의 원칙: **표는 AI 모델 카나리를 베끼고, 신호는 셀렉터 카나리를 재사용한다.** 새 물건을 옆에 하나 더 세우지 않는다.

### 0.1 그래서 이 문서가 진짜로 정하는 것 세 가지
1. 지금 `canary_runs` 는 **recipe 판을 담을 칸이 없다**(§3) — 이게 유일한 스키마 결정이다.
2. «통과»의 뜻을 **«돌았나»에서 «올바른 결과인가»로** 올린다(§5) — 이게 이 설계의 심장이다.
3. **넓히는 것은 사람이 볼 때만, 좁히는 것은 언제나**(§6·§8) — 기존 «자동 전환 X» 규칙과 화해시킨다.

## 1. 지금 있는 것 (그대로 쓴다 · 증거)

- 러너가 `--canary` 로 돌면 **하트비트**에 결과를 싣고, 서버가 `canary_runs` 에 UPSERT 한다
  (`lib/runner-jobs.ts:392` · `ON CONFLICT (day, channel) DO UPDATE`).
- 크론이 **KST 05:00** 에 하루 1회 평가한다(`runner-canary.ts` · `__eval__` 행 선점으로 잠금).
  실패 채널은 `runner_canary_down_suggested` 감사 + **제안만 · 자동 전환 X**(사람이 `ops-channels` 에서 누른다).
- `ok` 는 **3값**이다 — true / false / **null(판정 불가)**. null 을 실패로 세지 않는다(AC-9).
- 운영 조회는 `GET /api/ops-canary?days=14` (`netlify/functions/ops-runners.ts:66`).
- 드라이런 결과에 **`shotKey` 를 같이 돌려준다**(`runner/core.mjs`) — 운영이 «깨진 화면»을 찾아가는 열쇠다.
- AI 쪽 승격 규칙(`ai-model-watch.ts promoteRipeCanaries`): 24h 뒤 실패율 **≤0.34 승격 · ≥0.67 자동 롤백 ·
  그 사이는 한 주기 더 관찰** · 표본 0 이면 판정 안 함 · 롤백 대상은 `prev_chain` 에 보존.

🔴 **이 마지막 줄이 recipe 설계의 골격이다.** 우리 집에 이미 «3구간 판정 + 직전 판 보존 + 자동 롤백»이 서 있다. 그걸 그대로 쓴다.

## 2. recipe 의 모양 — 버전 · 서명 · 롤백

```
recipe {
  version:     "tistory@2026-09-16.1"   # 채널@KST날짜.연번 — 사람이 입으로 말할 수 있어야 한다
  channel:     "tistory"
  minRunner:   "1.1.6"                  # 이 판 미만 러너는 이 recipe 를 무시한다(새 표가 옛 실행기를 깨지 않게)
  selectors:   { titleBox, bodyBox, modeMenu, modeHtml, save, done, publish, tagBox, ... }
  waits:       { settleMs, editorMs }
  blockText:   ["자동입력 방지", "보안문자"]        # 차단 감지용 «보이는 글자»
  assertions:  { titleMaxLen, publicCheck: true }  # §5 판정 재료 — 표와 **함께** 내려온다
  sig:         HMAC-SHA256(RECIPE_SECRET, 정규화 JSON)
  rollbackTo:  "tistory@2026-09-15.2"   # 되돌릴 판 — **만들 때 채운다**
}
```

- **서명은 선택이 아니다.** recipe 는 «남의 브라우저에서 무엇을 누를지»를 정하는 값이다.
  서명이 안 맞으면 러너는 **묶여 온 표(zip 안의 표)로 돌아가 계속 일하고, 그 사실을 보고한다**(§6.2).
- 🔴 **`rollbackTo` 를 만들 때 채운다.** «되돌릴 판을 그때 찾자»는 사고 한가운데서 제일 안 되는 일이다.
  AI 쪽이 `prev_chain` 을 UPDATE 시점에 보존하는 것과 같은 규율이다.
- **불변**: 한 번 올린 `version` 의 내용은 안 바꾼다(러너 zip 과 같은 규율 —
  «같은 버전인데 다른 표»가 돌면 사고 때 무엇이 돌았는지 영원히 모른다).
- **`assertions` 가 표와 같이 온다**(§5). 표만 내려보내고 판정 기준을 러너 코드에 두면,
  표를 고칠 때마다 러너 업데이트가 필요해져서 recipe 를 만든 이유가 사라진다.

## 3. 🔴 스키마 — `canary_runs` 는 지금 recipe 를 담지 못한다

```
UNIQUE (day, channel)          -- 하루·채널당 딱 한 줄
```

- 그래서 **«이 카나리가 어느 recipe 를 시험했나»를 물어볼 수가 없다.**
- 같은 날 recipe 를 두 판 시험하면 **뒤엣것이 앞엣것을 덮어쓴다**(UPSERT).

> 🔴 **2026-09-15 정정 — 아래 «파괴적 DDL 이 필요하다»는 틀렸다.** 지우지 않고 남기되 왜 틀렸는지 적는다
> (지운 자리는 다음 사람이 다시 같은 결론에 이른다).

**결정(고침)**: `canary_runs` 에 **`recipe_version varchar(40)` · `stage varchar(12)` 를 더하기만 한다. 유니크는 그대로 둔다.**
⇒ **전부 추가형**이다. `DROP INDEX` 없다. **사장님 승인이 필요 없다.**

🔴 **왜 처음에 틀렸나**: 유니크 `(day, channel)` 을 «같은 날 두 판을 시험하지 못하게 막는 장애물»로 봤다.
그런데 **그 가정 자체를 이 문서 §7 이 금지한다** — «**동시 변경 1개**: 두 채널 표를 같은 날 올리지 않는다».
즉 «한 채널에 하루 한 recipe»는 내가 **원한 규칙**이고, 기존 유니크는 그걸 **막는 게 아니라 강제**한다.
흐름으로도 맞다: 그날 러너가 쓰는 표는 하나고 `--canary` 한 번이 그 표를 시험한다 —
**한 번 돌고 한 줄, 무엇을 시험했는지 이름표만 붙이면 된다.**

⚠️ 남는 것 하나: **배포 상태 표**(`recipe_rollouts` — 채널별 current/candidate/stage/승격·롤백 시각)는 **새 표**라
`db/schema.ts` 를 건드린다(B 전용 · CLAUDE §4.4). **표 자체는 `CREATE TABLE IF NOT EXISTS` 라 추가형**이고,
schema.ts 블록만 B 에게 넘기면 된다(메인 결정 2026-09-15).

## 4. 카나리 대상 선정 — 누가 먼저 맞나

| 단계 | 대상 | 통과 조건 | 최소 체류 |
|---|---|---|---|
| **0 우리·드라이런** | 우리 테스트 계정 · `--canary` 그대로(임시저장까지) | §5 의 1·2·3·5·6 | 즉시 |
| **1 우리·실발행** | 우리 소유 계정 1개 · **실발행 1건** | §5 **전부**(4번 포함) | **24시간** |
| **2 자원자** | «먼저 받아 볼래요»를 켠 고객(옵트인 · **기본 꺼짐**) | §5 전부 · 실패 0 | **24시간** |
| **3 전체** | 나머지 | — | — |

- 🔴 **왜 AI 처럼 `canary_pct=10` 이 아닌가**: 퍼센트는 **남의 계정에 먼저 떨어진다.**
  AI 모델은 우리 서버 안에서 글자만 바뀌지만, recipe 가 틀리면 **고객 블로그에 잘못된 글이 남는다.**
  되돌릴 수 있는 것과 없는 것의 차이라, 여기서는 **우리 계정이 먼저 맞는 순서**가 퍼센트보다 맞다.
- 🔴 **옵트인 없이 고객을 카나리로 쓰지 않는다.** 옵트인 화면에는 «무엇이 달라지는지 · 되돌릴 수 있는지»를 적는다.
- ⚠️ **자원자가 0명이면 2단계를 건너뛰지 않는다** — 1단계 체류를 **48시간**으로 늘린다(관문을 없애는 게 아니라 길게 잡는다).
- 표본이 0이면 **판정하지 않는다**(승격도 롤백도 안 한다) — AI 쪽 «표본 없으면 다음 주기까지 더 관찰»과 같다.

### 4.1 🔴 0단계의 전제 — **우리 테스트 계정에 예약이 서 있어야 한다**
`canary()` 는 큐에서 **진짜 `publish.*` 잡을 집어** 드라이런하고 **큐에 되돌린다**(`runner/core.mjs:259`).
잡이 없으면 `ok: null · step: "no_job"` 으로 끝난다 — 즉 **«시험할 글이 없으면 카나리는 아무것도 말하지 않는다.»**
⇒ recipe 배포를 켜려면 **우리 테스트 계정에 상시 예약 1건**이 서 있어야 한다. 이건 코드가 아니라 **운영 조건**이라
발주 트리거와 운영 체크리스트에 **명시**해야 한다(안 적으면 «카나리가 도는 줄 알았는데 매일 no_job» 이 된다).

## 5. 🔴 판정 — «돌았나»가 아니라 «올바른 결과인가»

이번 라운드에 실제로 겪은 것들이 이 절의 근거다. **«실패»보다 «틀린 성공»이 무섭다.**

| # | 단언 | 왜(겪은 사고) | 지금 있나 |
|---|---|---|---|
| 1 | 임시저장/발행 **도달** | 기본 | ✅ 지금 카나리가 본다 |
| 2 | **제목칸에 본문이 안 들어갔다**(제목 길이 ≤ N · 되읽기) | 실제로 그랬다(사장님이 화면 보고 발견) | ❌ 없다 |
| 3 | **제휴 고지가 본문 첫머리**에 있다 | DESIGN §16B.4 | ✅ `core.mjs disclosureIsFirst` 가 이미 본다 |
| 4 | (발행 단계면) **남이 볼 수 있다** — 글 주소를 **로그인 안 한 브라우저로** 열어 확인 | 🔴 **AC-55** | ❌ 없다(§10) |
| 5 | 확인창이 떴다면 **그 문구가 기록에 있다** | AC-42 — 조용한 취소를 드러낸다 | 🟡 티스토리만(이번에 넣음) |
| 6 | 누른 요소가 **보이는 것**이었다(숨은 복제본 아님) | AC-43 | 🟡 티스토리만(`visibleOf`) |

- 🔴 **4번이 이 설계의 심장이다.** «올렸다»는 우리 주장이고 **«남이 볼 수 있다»가 사실**이다.
  `button:has-text('공개')` 가 **«비공개»를 집어도**(AC-55) 발행은 «성공»하고 주소도 생긴다 —
  1번만 보는 카나리는 **그걸 초록으로 찍는다.** 반드시 **계정 세션이 아닌 곳에서** 열어 봐야 한다.
- `ok` 는 3값 그대로다: 단언을 **못 돌려봤으면 `null`**(판정 불가)이지 `false` 가 아니다(AC-9).
  실패한 단언 번호는 `step` 칸에 적는다(`assert4_not_public` 식) — 기존 `step` 의 쓰임과 같다.

## 6. 실패 판정과 자동 복귀

| 신호 | 판정 | 행동 |
|---|---|---|
| 카나리 단언 **1건이라도 `false`** | 즉시 | 그 recipe 를 **승격하지 않는다**(퍼지지 않는다) + 감사 `high` |
| 단언이 `null` 뿐(판정 불가) | 보류 | 승격도 롤백도 안 한다 — **한 주기 더 관찰**(AI 중간구간과 같다) |
| 🔴 그 보류가 **72시간** 넘게 이어짐 | 포기 | **승격을 취소**하고 candidate 를 지운다 + 운영 알림(§6.3) |
| 퍼진 뒤 한 채널에서 **연속 3건 실패** | 자동 | `rollbackTo` 로 **자동 복귀** + 감사 `high` + 운영 알림 |
| 같은 recipe 로 **서로 다른 3개 테넌트**에서 실패 | 자동 | 위와 같음(한 고객의 계정 문제와 가른다) |
| 서명 불일치 · `minRunner` 미달 · 서버 못 붙음 | 러너가 즉시 | **묶여 온 표**로 일하고 **보고한다** |

### 6.1 🔴 «자동 전환 X» 규칙과의 화해
기존 셀렉터 카나리는 실패해도 **제안만** 한다(자동으로 채널을 내리지 않는다). 이 설계는 **자동 복귀**를 넣는다. 모순이 아니다:

| 행동 | 무엇인가 | 자동? |
|---|---|---|
| 채널 `down` 전환 | **고객 발행을 멈추는 것** — 새 피해 | 🔴 사람이 (지금 그대로) |
| recipe 롤백 | **어제 되던 상태로 되돌리는 것** — 피해 원상복구 | ✅ 자동 |
| recipe 승격 | **더 많은 사람에게 퍼뜨리는 것** | 🔴 사람이 · 시간 게이트(§8) |

기준 한 줄: **«되돌아갈 곳이 이미 돌던 판이면 자동, 새로 멈추거나 새로 퍼뜨리면 사람.»**
AI 쪽도 정확히 이렇게 한다(`ai_candidate_rollback` 은 자동 · high 감사).

### 6.2 최후의 보루
🔴 recipe 를 **못 받거나 못 믿으면 러너는 멈추지 않는다** — zip 에 묶여 온 표로 어제처럼 일한다.
**배포는 편의고 발행이 본업이다**(자동 업데이트에서 세운 규율과 같다).
⚠️ 단 **복귀가 조용하면 안 된다** — 되돌아간 러너 수가 §9 에 보여야 한다. 안 보이면 «전부 새 표를 쓰는 줄» 안다.

### 6.3 🔴 «영원히 대기»를 막는다 (내가 처음 쓴 설계의 구멍)
초안은 «`null` 이면 한 주기 더 관찰»만 적었다. 그런데 `no_job`·`session_expired` 는 **계속 `null` 을 낸다**(§4.1) —
그러면 그 recipe 는 **승격도 롤백도 안 된 채 영원히 candidate 로 남는다.** 화면에는 «카나리 도는 중»으로 보인다.
이 프로젝트가 제일 싫어하는 모양(**조용히 멈춰 있는데 초록**)이라 **기한을 못 박는다**:

- 판정 불가만 **72시간** 이어지면 **승격을 포기**한다(candidate 폐기 · 기존 판 유지 · 감사 `medium`).
- 포기는 **실패가 아니다** — «시험을 못 했다»로 적는다(AC-9: 모른다 ≠ 나쁘다). 다시 올리면 된다.
- §9 의 «왜 대기 중인가»에 **남은 시간**을 같이 보여 준다.

## 7. 부분 배포 — 채널별 · 단계별

- **채널별로 따로.** 티스토리 표를 고치는데 네이버가 같이 흔들릴 이유가 없다(`recipe.channel` 이 단위).
- **단계별 보수성**: `selectors.publish` 처럼 **되돌릴 수 없는 동작**의 셀렉터는 한 급 더 조심한다(0·1단계 체류 2배).
  임시저장 셀렉터가 틀리면 다시 하면 되지만, **발행 셀렉터가 틀리면 남의 눈에 글이 나간다.**
- **동시 변경 1개**: 두 채널 표를 같은 날 올리지 않는다(사고가 나면 어느 쪽인지 못 가른다).

## 8. 🔴 시간 게이트 — 아무도 안 볼 때 퍼지지 않게

| 규칙 | 값 |
|---|---|
| **승격**(다음 단계로 넓히기) | **KST 10:00~18:00 · 평일**에만 |
| 그 밖의 시간 | 카나리는 돌되 **승격만 멈춘다**(다음 영업시간에 사람이 보고 넘긴다) |
| **자동 복귀(롤백)** | 🔴 **시간 제한 없음 — 언제나 즉시** |
| 카나리 평가 | 기존대로 **KST 05:00**(평가는 승격이 아니다 — 재료만 만든다) |

**넓히는 것은 사람이 볼 때만, 좁히는 것은 언제나.** 이 비대칭이 ⑤번 답이다.

⚠️ AI 모델 카나리에는 이 게이트가 **없다**(24h 지나면 언제든 승격). 여기만 더 조이는 이유:
AI 는 우리 서버 안이고, **recipe 는 남의 계정에서 버튼을 누른다.**
⚠️ 긴급 수리(채널이 화면을 바꿔 전 고객이 멈춤)도 **0·1단계는 건너뛰지 않는다** —
급할수록 «틀린 성공»이 난다(급히 만든 표일수록 §5-4 를 못 지킨다).

## 9. 운영 화면이 봐야 할 신호

`GET /api/ops-canary` 를 넓히는 쪽으로 간다(새 화면을 만들지 않는다).

| 신호 | 왜 |
|---|---|
| 채널별 **지금 퍼진 recipe 버전** + 단계별 러너 수 | «누가 무엇을 쓰고 있나» |
| 🔴 **묶여 온 표로 되돌아간 러너 수** | 조용한 복귀를 드러낸다(§6.2) |
| **단언별** 통과/실패(§5 의 6줄 그대로) + `shotKey` | «돌았다»가 아니라 **어느 단언이** 깨졌나 · 화면으로 바로 간다 |
| 마지막 자동 복귀 **시각·사유·되돌아간 판** | 사고 복기의 시작점 |
| 승격 대기 recipe + **왜 대기 중인가**(시간게이트/체류미달/자원자0/판정불가) | 멈춰 있는 이유가 보여야 한다 |

## 10. 🔴 이 조사에서 나온 **별건 결함** (recipe 와 무관 · 지금 코드에 있다)

**`verify.post_alive` 는 «우리가 비공개로 발행한 글»을 잡지 못한다.**

- 근거: 잡은 **그 계정의 로그인된 프로필**에서 돈다 —
  `runner/core.mjs` 가 `profileKey: account.profileKey` 로 컨텍스트를 열고 `applyCookies(ctx, account.cookies)` 를 태운다.
- `runner/channels/post-alive.mjs` 는 본문에서 `비공개입니다` 류 문구를 찾아 죽음을 판정하는데,
  **글쓴이 자신의 눈으로 열면 비공개 글도 정상으로 보인다.** 그 정규식은 **남의 비공개 글에만** 걸린다.
- ⇒ AC-55 형 «비공개로 성공»은 발행 때도, **7일 뒤 확인 때도** 안 잡힌다.
  우리가 가진 유일한 사후 확인이 이 구멍을 **그대로 공유한다.**
- 당장 터지지는 않는다(**실발행 0건** — 7일 뒤 잡이 생길 글이 아직 없다). 그래서 **급하진 않고, 확실히 남겨야 한다.**
- 고치는 법(작다): post_alive 만 **쿠키 없는 새 컨텍스트**로 열거나, 같은 주소를 한 번 더 익명으로 확인한다.
- 🔴 **이번엔 안 고쳤다** — 메인 지시가 «R8 설계 · 코드 0» 이라서다. **발주하면 즉시 한다**(§5-4 와 같은 고침 하나로 둘 다 닫힌다).
