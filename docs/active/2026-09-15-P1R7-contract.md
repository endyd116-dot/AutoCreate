## §1 B-1 — 영상 축 개통(0→100%)

### 1.1 (0→20%) 설정 «영상 만들기» 토글 + 기존 테넌트 마이그레이션
- `GET/POST /api/tenant-settings` 의 `kinds` 를 화면에서 켤 수 있게(A §5.1) — 서버는 이미 받는다. **기존 테넌트 보정**: `kinds` 가 없거나 `["text"]` 인 곳은 그대로 두되, 토글을 켜면 `["text","video"]` 로 저장(덮어쓰기 금지 · 병합).
- 🔴 온보딩을 안 거친 테넌트(`settings.kinds` 자체가 없음)도 토글이 보여야 한다(기본값 표시 = 꺼짐).

### 1.2 (20→45%) 계정 없이 영상 만들기
- `director.ts:174` 「영상 채널 계정이 있을 때만 영상 piece」 규칙을 **완화**: `kinds` 에 video 가 있으면 **계정 없이도** `kind:"video"` piece 를 만들 수 있다(슬롯 없는 자동 생성 금지 규칙(§4.7)은 그대로 — **수동 «만들기» 경로만** 허용).
- 계정 미배정 영상 piece 는 발행 단계에서 `awaiting_manual`(«앱에서 올려 주세요») — 조용한 실패 0.
- 만들기·디렉터 화면의 «영상» 선택지는 A §5.2.

### 1.3 (45→70%) mp4 내려받기 · 올린 주소 적기
- `GET /api/piece-video?id=` → `{ ok, url(presign 10분), filename:"AC-{pieceId}-{slug}.mp4", bytes, durationSec }` · 없으면 404 `step:"no_render"`. **파일명은 한 곳에서**(B2 `releaseFilename` 관례) · `ResponseContentDisposition` 서명에 담는다(AC 러너 배포에서 배운 것).
- `POST /api/post-mark-published { pieceId, url }` → 직접 올린 주소를 `posts` 1행으로(멱등 `external_url` 유일 · 이미 있으면 200 그대로) · piece `published` · 슬롯 동기화 · 감사 `post_marked_manual` · **수익 매칭 대상이 된다**.
  - 400 `step:"url"`(https·채널 도메인 대조 · 남의 도메인 거부) · 403 tenantAllowed.
  - 🔴 **«수익 매칭 대상» 은 주소만으로는 안 된다**(B-1 2026-09-15 발견): 유튜브 수익은 `posts.external_url` 이 아니라 **`posts.channel_ref`(영상 id)** 로 붙는다(`lib/revenue/youtube.ts:35`) → 주소에서 **커넥터와 같은 모양으로** ref 를 되뽑아 저장한다(youtube videoId · instagram mediaId · threads id · tiktok video id). 모양이 코드로 안 굳은 채널(네이버·티스토리·블로거·WP)은 **비워 둔다** — 틀린 ref 는 없는 ref 보다 나쁘다(애드센스는 external_url 로 귀속하므로 손해 0).

### 2.5 (신설 · 사장님 지시 2026-09-15) 🔴 계정 하나 = IP 하나 — «연좌제 정지» 방어

> 사장님: «쓰레드에 영상 올렸다 정지먹으면 그 계정 수익이 다 죽는다. 그래서 계정을 여러 개 만드는데, **한 IP 에서 여러 계정을 굴리다 하나 정지되면 그 IP 를 쓴 계정이 연좌제처럼 다 죽는다.** IP 를 여러 개 사서 계정별로 붙일 수 있나?»
> **답: 러너로 올리는 채널은 된다(자리는 이미 있고 «실제로 도는 것»이 없다). API 로 올리는 채널(유튜브·인스타·쓰레드)은 우리 서버 IP 로 나가므로 따로 태워야 한다.**

**지금 상태(실측)**
- `accounts.proxy_url` 칸 있음 · 러너 `openContext` 가 계정별 프록시를 브라우저 컨텍스트에 건다 · 계정별 영구 프로필(쿠키·지문 분리) · 계정 간 30분 간격 · 유사도 게이트 — **여기까진 있다.**
- 🔴 **구멍 1: 프록시 주소가 깨져 있으면 «프록시 없이» 그냥 나간다**(`runner/lib/browser.mjs:45` 의 `catch` — «발행을 막지 않는다»). 이게 정확히 연좌제를 부른다.
- 🔴 **구멍 2: 나가는 IP 를 아무도 확인하지 않는다** — 프록시가 붙었다고 믿을 뿐 실제 출구 IP 기록이 0.
- 🔴 **구멍 3: 유튜브·인스타·쓰레드는 서버 `fetch` 로 올린다**(`lib/publish/youtube.ts:129` 등) → **모든 고객이 우리 Netlify IP 공유**. 프록시 자리 자체가 없다.
- 프록시를 사서 넣고·바꾸고·죽었는지 보는 **관리 표·화면이 0**(칸 하나에 사람이 손으로 붙이는 게 전부).

**이번 라운드에 만드는 것**
1. **프록시 표** `proxies`(추가형 DDL): 공급사 · 유형(주거/모바일/데이터센터) · 지역 · 접속 주소(암호화 · 자격과 같은 취급) · **sticky 세션 키** · 상태(`active|down|expired`) · 마지막 점검 시각 · 마지막 출구 IP · 월 원가.
2. **배정**: 계정 1 : 프록시 1(유일 제약) · 관리형은 우리가 자동 배정 · 내 PC 러너는 고객이 넣거나 우리가 판다. 운영센터 «러너» 아래 프록시 배정 화면(A 는 다음 라운드 · 이번엔 운영 API 까지).
3. 🔴 **fail-closed** — 프록시가 배정된 계정은 **프록시 없이는 절대 안 나간다**: 주소 파싱 실패·연결 실패·인증 실패 전부 **발행 중단 + `account_health` 기록 + 알림 «IP 연결이 끊겨 잠시 멈췄어요»**. `browser.mjs` 의 조용한 폴백을 없앤다. (기존 «프록시 없는 계정»은 그대로 직결 — 소급 0.)
4. 🔴 **출구 IP 확인이 곧 증거** — 잡 시작 시 컨텍스트로 IP 확인 1회(`api.ipify.org` 같은 가벼운 곳) → `accounts.last_exit_ip` 기록 · **배정된 프록시의 기대 IP 와 다르면 발행 중단**(프록시가 죽고 조용히 우회한 상태를 여기서 잡는다) · 계정마다 IP 가 겹치면 운영 경고(«두 계정이 같은 IP 로 나갑니다»).
5. **API 채널(유튜브·인스타·쓰레드)**: `lib/publish/*` 의 서버 `fetch` 에 **계정별 프록시 dispatcher**(undici `ProxyAgent`)를 끼울 수 있는 자리를 만든다 — 기본은 지금대로 직결, 계정에 프록시가 있고 `PROXY_API_PUBLISH=1` 이면 그 프록시로. 🔴 **정직 표기**: 이 채널들은 IP 말고도 **앱 단위**로 묶일 수 있다(우리 OAuth 앱 하나를 전 고객이 공유) — IP 분리로도 그건 못 막는다. 화면·문서에 «IP 는 나눠 드리지만, 플랫폼 규칙 위반은 앱 전체에 영향이 갈 수 있어요»를 적는다.
6. **원가표** `docs/active/2026-09-15-proxy-cost.md`: 주거 프록시 공급사 3곳 비교(계정당 월 원가 · 한국 IP 가능 여부 · sticky 지원 · 대역) → §2.4 관리형 «계정당 월요금(프록시 포함)» 근거. 사장님 결정 7(가격)의 입력.
7. **정지 대비 승계와 연결**: `account_groups`(표는 있는데 **쓰는 코드 0** · 전수조사 §7.1 ❌)를 살려 «같은 채널·같은 니치 계정 묶음» = 승계 단위로. 한 계정이 정지되면 같은 그룹의 **다른 IP·다른 프로필** 계정으로 예약이 옮겨간다(이미 있는 `reassignSlots` 가 그룹을 본다).

**이번 라운드에 안 하는 것**: 프록시 실제 구매·배정(사장님 합동 세션) · 프록시 자동 구매 API · 모바일 프록시 · 계정별 전화번호/이메일 분리(고객 몫 — 안내 문서로).
