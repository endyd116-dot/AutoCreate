## 1. 🔴 계정 신원 — «로그인된 블로그 주소»를 실제로 읽나 (AC-201)

**왜 못 쟀나**: 이 PC 에 로그인된 네이버 프로필이 없다(발행한 러너는 «걷기시험 PC»). 로그아웃 쪽(→ `nidlogin`)만 봤다.

```
cd runner
AC_PROBE_PROFILE=<그 계정 프로필 경로> node probe-identity.mjs
```

| 통과 | 실패 |
|---|---|
| `readMyBlogId` 가 `{ blogId: "<실제 아이디>", via: "myblog" }` | `blogId: null` 이면 **그 방법이 안 되는 것** — 다른 길을 찾아야 한다 |
| 판정이 `match`(장부와 같으면) | `mismatch` 면 장부의 `handle` 이 실제 블로그 주소와 다른 것(정상일 수 있다 — 확인 단추가 그 자리다) |

⚠️ **쓰기 0** — 페이지 두 개를 열어 읽기만 한다.

## 2. 자막 폰트 — 다른 PC 에서 실제로 구워 보기 (AC-202)

**왜 못 쟀나**: 이 PC 에선 **브라우저까지만** 쟀다(동봉 전 `error`/1605.57 → 동봉 후 `loaded`/1427.44). ffmpeg 로 실제 굽는 것은 안 했다.

```
cd runner

```
| 통과 | 실패 |
|---|---|
| 판정 `bundled (Pretendard)` · `@font-face` status `loaded` | `fallback` 이면 **그 PC 에 폰트가 안 갔다** — zip 에 `.woff2` 가 들어갔는지부터 본다 |

🔴 ② **굽기까지 보려면** 카나리 렌더 잡이 필요하다(`render.video`). 그때 `formatMarks.subtitleFont` 가 보고에 실리는지 같이 본다 — **경로 세 군데를 이어 놨으니 거기서 끊기면 그게 실증**이다.

## 3. 🔴 막힌 까닭 — **실물 화면의 낱말** (AC-203) · 제일 값진 줄

**왜 못 쟀나**: 신호표를 **코드에 있던 낱말로만** 채웠다. 안 겪어 본 화면의 문구를 상상해 넣으면 **그게 또 틀린 사유**가 된다.

그날 할 것 — **막힌 화면을 실제로 한 번 본다**:
```
cd runner
RUNNER_SHOTS=1 node ac-runner.mjs --canary --headed
```
1. 카나리가 에디터까지 간다(임시저장까지 · **발행 0**).
2. 🔴 **그 화면의 `innerText` 를 통째로 받아 적는다** — 막히지 않아도 «정상 화면의 낱말»을 알아 둬야 대조군이 생긴다.
3. 가능하면 **일부러 막히는 화면**을 한 번 본다(예: 잠깐 로그아웃하고 에디터 열기 → «로그인이 필요» 화면).

| 무엇을 적어 올 것 | 왜 |
|---|---|
| 정상 화면 낱말 | 대조군 — 신호가 **정상 화면에도** 걸리면 거짓 양성이다 |
| 로그인 풀린 화면 낱말 | 지금 `로그인이 필요\|다시 로그인\|nidlogin` 로 잡는다 — **실물과 맞나** |
| (운 좋으면) 제재·잦음 화면 | 🔴 지금 표의 낱말은 **AM 에서 온 것**이고 우리가 본 적은 없다 |

⇒ 받아 온 낱말을 `runner/lib/block-reason.mjs` 의 `NAVER_PUBLISH_SIGNALS` 에 넣고
   `scripts/verify-block-reason.mts` 판정표에 **그 줄을 더한다**(그래야 다음에 안 깨진다).

## 4. 사람 리듬 — 고치기 전에 **확인할 길** (AC-204)

**왜 안 고쳤나**: 잰 값은 있다 — 입력 **상수 6·8·12ms**(6ms = 초당 166자) · 스크롤 **0** · 마우스 이동 **0** · 문단 사이 멈칫 **0**.
🔴 그런데 **글 넣는 길은 이 리포가 문단 증발·서식 번짐으로 두 번 데인 자리**이고, 지금은 공개 발행 0 이라
**고쳐도 실물로 확인할 길이 없다.** 확인 못 하는 변경을 그 길에 넣는 것이 «넣었다고 말하기»다.

### 🔴 그래서 **확인할 길을 먼저 만들어 뒀다** — 그날 이 순서로 한 번에 본다

**재는 자(이미 있다)**: `runner/lib/format-bleed.mjs` 의 `measureFormatBleed`·`paragraphVerdict` —
**러너가 발행 직전에 이미 문단 수와 번짐을 센다.** 리듬을 고쳐도 **그 숫자가 안 변해야** 한다.

| 단계 | 무엇 | 통과 기준 |
|---|---|---|
| ① 기준 | 리듬 **고치기 전** 카나리 1회 | `formatMarks.paragraphs` 의 `expected`/`actual`/`kind` · `bleed.pct` 를 적어 둔다 |
| ② 고침 | 입력 속도에 흔들림을 넣는다(낱말 사이·문장 끝에 더 쉰다) | — |
| ③ 대조 | **같은 글**로 카나리 1회 | 🔴 `paragraphs.kind` 가 `ok` 그대로 · `actual` 이 **①과 같은 수** · `bleed.pct` 가 안 늘었다 |
| ④ 되돌림 | ③이 어긋나면 **곧바로 되돌린다** | 문단이 하나라도 줄면 그 변경은 버린다 |

🔴 **대조군이 같은 영상 안에 있어야 한다** — «리듬만» 다르고 글·사진·채널이 같아야 원인 귀속이 된다.
⚠️ 스크롤·마우스 이동은 ③이 초록으로 두 번 나온 **뒤에** 손댄다. 한 번에 둘을 바꾸면 어느 쪽이 깼는지 모른다.

## 5. ⊘ 지금도 앞으로도 **원리적으로 못 재는 것**

- **«파싱은 되는데 과녁이 틀린» 셀렉터** — `scripts/probe-dead-selectors.mjs` 는 «문법적으로 죽었나»까지다.
  과녁이 맞나는 **그 화면을 봐야** 안다.
- **서버 레시피로 오는 셀렉터의 «과녁»** — 값이 소스에 없다. 모양은 `selector-guard` 가 막지만 **맞는지는 못 본다.**
- **채널이 우리를 «기계»로 보나** — 리듬을 고쳐도 «그래서 덜 막히나»는 **여러 번 발행해 봐야** 안다. 한 번으로는 못 답한다.
