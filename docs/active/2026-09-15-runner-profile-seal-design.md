# 러너 프로필 봉인 — 설계 (B2 · P1R8 §3.1 / ④11 · 2026-09-15)

> 계약 §3.1: «🔴 **키를 어디 두는가가 전부다** — 고객 PC 에 키와 자물쇠를 나란히 두면 암호화가 아니다.
> 설계를 먼저 한 줄로 보고하고 내 승인 뒤 구현.»
> **이 문서는 승인을 받으려고 쓴 것이다. 코드는 §7(측정)만 썼다** — 측정은 아무것도 안 바꾸고, 안 재면 이 설계의 값을 모른다.

---

## 0. 한 줄

**«복사해 가면 안 열린다»를 만든다.** 그 이상은 못 만들고, 못 만든다고 적는다.

---

## 1. 🔴 먼저 — 우리가 **막을 수 없는 것**부터

이걸 먼저 적지 않으면 아래 설계가 장식이 된다.

| 위협 | 막나 | 왜 |
|---|---|---|
| 러너 폴더를 **다른 PC 로 복사** | ✅ | 서버가 쥔 키 없이는 안 열린다 — **이 설계의 전부** |
| 폴더가 **백업·동기화 폴더**(OneDrive·Dropbox)에 얹혀 나감 | ✅ | 같은 이유 |
| 기기를 잃어버렸을 때 **나중에 막기** | ✅ | 서버가 키를 안 준다(= **DPAPI 로는 못 하는 것** · §4) |
| 그 PC 에서 **그 사용자로 코드를 돌릴 수 있는 사람** | ❌ | 러너가 풀 수 있으면 그 사람도 푼다. **원리상 불가능하다** |
| 잡이 도는 **그 몇 분 동안** 폴더를 훔쳐 감 | ❌ | 그때는 풀려 있어야 크로미움이 쓴다 |

🔴 **②를 막는다고 적는 설계는 거짓말이다.** 우리가 파는 것은 «복사본은 쓸모없다»이고, 그건 진짜로 값이 있다.

---

## 2. 지금 상태 — 실측과 **못 잰 것**

| 플랫폼 | 크로미움이 쿠키를 어떻게 잠그나 | 판정 |
|---|---|---|
| **Windows** | `v10` = AES-256-GCM · 키를 **DPAPI** 가 기기+사용자에 묶는다 | ✅ 이미 잠겨 있다(직전 B2 실측) |
| **Linux · 키링 있음** | `v11` = 키링(gnome-keyring·kwallet)에서 파생한 키 | ✅ |
| 🔴 **Linux · 키링 없음** | `v10` = **하드코딩 키**(공개된 값) → 사실상 평문 | ❌ **구멍** |
| **macOS** | `v10` = Keychain 파생 | ⬜ **재 본 적 없다**(맥이 없다) |

🔴 그리고 **하나 더 못 잰 것**: 라이브에 러너 16대가 있는데 **그중 몇 대가 리눅스인지 우리는 모른다.**
`runner_devices` 에 OS 칸이 없다. ⇒ §7 이 이걸 먼저 잰다.

⚠️ 🔴 **«v10 이면 위험»이 아니다** — 같은 `v10` 이 Windows 에선 DPAPI, 맥에선 Keychain, 리눅스에선 하드코딩이다.
플랫폼을 같이 안 보고 접두사만 보면 **멀쩡한 Windows 16대를 «평문»이라고 보고**하게 된다(AC-57 · 거짓 false 는 거짓 true 보다 나쁘다 · AC-67).

---

## 3. 🔴 중요한 사실 하나 — **세션의 정본은 이미 서버에 있다**

코드를 읽고 알았다(설계를 쓰기 전에 확인해야 했던 것):

- 서버가 쿠키를 **AES-256-GCM 으로 들고 있다** — `account_creds(kind='cookies')` · `saveRunnerSession()`.
- claim 때 그 쿠키를 러너에 **내려 준다** — `loadAccountForRunner()` → `runner/core.mjs` 의 `applyCookies(ctx, account.cookies)`.

⇒ **고객 PC 의 프로필 폴더는 «세션»이 아니라 «캐시»다.** 그럼 왜 남기나 — 두 가지 때문이다:

| 프로필이 들고 있는 것 | 쿠키로 대신되나 |
|---|---|
| `localStorage` · `IndexedDB` 로그인 상태 | ❌ (네이버·카카오가 쓴다) |
| **브라우저 지문의 연속성** | ❌ — 🔴 매번 새 브라우저로 들어가는 것이 **자동화처럼 보인다**(AC-19 캡차를 부른 그 축) |

⇒ 그래서 **«프로필을 아예 안 남긴다»는 답이 아니다**(계정 건강을 깎는다). **봉인**이 답이다.

---

## 4. 설계 — 서버가 쥔 키로 봉인

```
account_creds(kind='profile_key')   ← 계정당 32바이트 난수 · CREDS_ENC_KEY 로 암호화 저장(기존 금고 재사용)
        │  claim 응답에 실려 내려간다(쿠키가 이미 가는 그 길 · 평문 표면을 **늘리지 않는다** · §4.7)
        ▼
러너:  잡 시작 → profiles/{key}.sealed  ──복호화──▶  profiles/{key}/   (평문 · 잡 동안만)
       잡 끝(finally) → 세션 파일만 ──암호화──▶ .sealed → 평문 폴더 삭제
```

### 4.1 무엇을 봉인하나 — **전부가 아니다**
크로미움 프로필은 캐시 때문에 수백 MB 가 된다. 잡마다 그걸 암·복호화하면 **발행이 느려지고 디스크가 닳는다.**
봉인 대상은 **세션을 지닌 것만**:
`Default/Cookies`(+`-journal`) · `Default/Network/Cookies` · `Default/Local Storage/leveldb/` · `Default/IndexedDB/` · `Default/Login Data` · `Default/Preferences`
🔴 `Default/Cache`·`Code Cache`·`GPUCache` 는 **안 담는다**(크고 값이 없다).

### 4.2 🔴 실패는 **열어 둔다**(fail-open) — 프록시와 정반대다
프록시는 fail-closed 였다(잘못 나가면 연좌제). 여기는 반대다:
**봉인이 실패했다고 잡을 멈추면, 고객은 로그인을 잃고 재로그인을 반복하다가 캡차를 부른다**(AC-19 · 우리가 이미 한 번 그랬다).
⇒ 복호화 실패 = **기존 평문 폴더 그대로 쓰고 보고한다.** 암호화 실패 = **평문 폴더를 지우지 않는다.**
🔴 **«안전을 위해 고객 계정을 죽이는» 거래는 안 한다.** 다만 **조용히 넘어가지 않는다** — 하트비트에 실어 운영이 본다.

### 4.3 키가 도는 길
- 키는 **계정당 1개**(기기당이 아니다) — 같은 계정을 두 PC 에서 굴릴 수 있어야 한다.
- 로테이션: `/api/runner-rotate` 가 토큰·지문을 초기화할 때 **프로필 키는 건드리지 않는다**(건드리면 그 순간 모든 세션이 죽는다).
  키를 새로 내려면 **봉인 해제 → 새 키로 재봉인**이 러너 쪽에서 한 번 일어나야 한다 — 그건 별도 잡이다(범위 밖).
- 🔴 **폐기**: 기기를 잃어버리면 운영이 그 테넌트의 `profile_key` 를 폐기(purge)한다 →
  훔쳐 간 `.sealed` 는 **영원히 안 열린다.** ← **DPAPI 로는 못 하는 일이고, 이 설계의 진짜 값이다.**

### 4.4 비용
| 무엇 | 값 |
|---|---|
| 잡당 추가 시간 | 세션 파일만 담으면 대개 **수 MB** → 1초 안쪽(측정 필요) |
| 디스크 | 봉인본 + 잡 동안의 평문 = 한때 2배 |
| 🔴 새로 생기는 위험 | **봉인이 깨지면 로그인을 잃는다** → §4.2 fail-open 과 §6 단계 배포로만 감당한다 |

---

## 5. 🔴 그래서 — **Windows 에는 값이 작다**

| 플랫폼 | 봉인으로 새로 얻는 것 |
|---|---|
| Windows | **폐기 가능성만**(복사 방어는 DPAPI 가 이미 한다) |
| macOS | 같음(Keychain 이 이미 한다고 **추정** — 못 쟀다) |
| 🔴 **Linux 키링 없음** | **거의 전부** — 지금은 복사하면 열린다 |

⇒ 정직한 우선순위: **①리눅스가 몇 대인지부터 재고 ②거기부터 켠다.** Windows 16대에 비용을 먼저 쓰는 것은 순서가 틀렸다.
🔴 그리고 이 문장이 §7 을 «나중 일»이 아니라 **선결**로 만든다.

## 6. 단계 배포 (승인 시)

| 단계 | 무엇 | 되돌리기 |
|---|---|---|
| 0 | §7 측정 — 기기별 OS·봉인 상태를 하트비트로 모은다 | 해당 없음(읽기만) |
| 1 | 우리 실증 기기 1대에서 봉인 켜기 · 발행 1건 왕복 | 키 폐기 → 평문 폴더 그대로 |
| 2 | **리눅스 기기만** 켜기(측정으로 고른다) | 서버 플래그 한 개 |
| 3 | 전체 | 〃 |

🔴 **한 번에 켜지 않는다** — 프로필이 깨지면 고객이 재로그인을 하고, 재로그인 반복이 캡차를 부른다(우리가 이미 밟은 길).

## 7. 지금 만든 것 — **측정만**(승인 불필요 · 아무것도 안 바꾼다)

### 7.0 🔴 이 PC 실측 (2026-09-15 · `probeFleet` 을 진짜로 돌린 값)

```
{ platform:"win32", profiles:27, sealed:5, weak:0, unknown:0, state:"os", copySafe:true }
  · 로그인 정보 보관: 윈도우가 이 PC·이 사용자에게 묶어서 잠갔어요(DPAPI) (로그인 5개)
```
- 로그인이 든 프로필 **5개**(네이버 2·티스토리 3) — 전부 `v10` 18~26개, 즉 **DPAPI 로 봉인돼 있다**. 직전 B2 의 실측이 맞았다.
- 나머지 **22개는 드라이런 찌꺼기**(쿠키 파일 자체가 없다).
- 🔴 **음성 대조**: 같은 폴더를 `platform:"linux"` 로 보면 `state:"weak" · weak:5 · copySafe:false` 가 나오고
  경고 문구가 뜬다 — 판정이 **진짜로 갈린다**는 확인이다(«전부 안전»이라고 말하는 검사가 아니다).

### 7.1 🔴 돌려 보고서야 잡힌 결함 **둘** (둘 다 조용한 종류였다)

| 무엇 | 처음 동작 | 왜 나쁜가 |
|---|---|---|
| «파일이 없다» ↔ «못 읽었다» 를 한 칸으로 뭉갬 | 찌꺼기 22개가 전부 `unknown` → 기기 판정이 통째로 **«확인 불가»** | 운영 화면이 «전 기기 확인 불가»로 보이고 **진짜 못 잰 기기가 그 안에 숨는다**(AC-9 의 한 층 아래) |
| 대표값 순위에서 `none` 을 «나쁜 쪽»에 둠 | 로그인 5개가 **멀쩡히 잠긴** PC 를 **«아직 로그인한 적이 없어요»**로 보고 | 있는 것을 없다고 말한다 — 그 상태로는 아무도 이상하다고 느끼지 않는다 |

⇒ 둘 다 `scripts/verify-profile-seal.mjs` 에 **임시 폴더를 진짜로 만들어** 못 박았다(순수 함수만으로는 순위 결함이 안 잡힌다).

### 7.2 만든 것

`runner/lib/profile-seal.mjs`
- 크로미움 쿠키 파일에서 값 접두사(`v10`/`v11`) 개수를 세고, **플랫폼과 함께** 판정한다.
- 🔴 판정은 **순수 함수**(`classifyProfileSeal`)로 뽑았다 — 이 판정이 조용히 틀리면
  «멀쩡한 Windows 를 평문이라고 보고»하거나 그 반대가 되고, 둘 다 라이브로는 영영 안 보인다(AC-68).
  그래서 `scripts/verify-profile-seal.mts` 가 **막아야 할 것과 통과시켜야 할 것을 같은 수만큼** 잰다.
- 못 읽으면 **`unknown`** 이다 — «안전»도 «위험»도 아니다(AC-9).
- 하트비트 `caps.profileSeal` 로 올라가 운영이 **기기별로** 본다.

## 8. 승인받을 것 (메인 → 사장님)

1. **§4 를 만드나** — 계정당 프로필 키를 서버가 쥐고 claim 때 내려 주는 구조.
2. **§4.2 fail-open** — 봉인이 깨져도 발행을 막지 않는다(안전보다 계정 생존을 앞에 둔다).
3. **§5 우선순위** — 리눅스부터. Windows 는 «폐기 가능성»만 얻으므로 뒤로.
4. ⚠️ **맥은 여전히 못 쟀다** — 맥 기기가 생기기 전까지 «추정»으로 둔다(§7 이 실제 기기에서 답을 준다).
